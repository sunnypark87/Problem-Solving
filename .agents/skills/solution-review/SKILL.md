# 풀이 리뷰·분류·문제 맵

사용자 풀이를 리뷰하고 개선한 뒤 알고리즘에 맞는 폴더로 분류한다. 관련 README는 문제를 찾기 위한 맵과 주요 개념 요약으로 관리한다. 설명은 한국어, 코드·식별자·경로는 원래 언어를 유지한다.

## 범위와 형식 참조

- 대상 파일, 적용되는 AGENTS.md, 목적지와 상위 폴더의 README를 읽는다. 사용자 지정 범위가 이 기본 흐름보다 우선한다. 주석만 요청하면 실행 코드 변경·이동·README 갱신을 하지 않는다.
- 기본 형식 참조는 저장소의 `Programmers/Cpp/03_Graph/01_BFS_DFS/L3_네트워크.cpp`다. 존재하면 현재 내용을 읽고 사용자 편집 스타일을 따른다. 사용자가 다른 참조를 지정하면 그것을 우선한다. 참조가 없으면 아래 형식을 사용한다.
- 기본적으로 리뷰 주석 → 개선된 실행 코드 → 파일 하단의 원본 풀이 블록 주석 순서로 작성한다. 기존 main·로컬 테스트와 사용자 주석은 보존한다. 원본은 이번 리뷰 전 사용자의 실제 풀이를 보관하며 이미 보관된 원본을 덮어쓰거나 중복 추가하지 않는다.
- 개선할 필요가 없으면 실행 코드는 유지하고 원본 사본도 추가하지 않는다. 기존 리뷰가 있으면 해당 영역만 갱신한다. 요청 없이 커밋·푸시하지 않는다.

## 리뷰 주석 형식

include/import 및 필수 파일 머리말 뒤, 첫 풀이 함수 앞에 리뷰를 둔다. C++/JavaScript는 아래 블록 주석을 사용하고 다른 언어는 실제 주석 문법으로 작성한다.

```text
// 풀이 리뷰 및 개선
/*
- [풀이 방식과 결과가 성립하는 이유를 1~2문장으로 요약]

- 시간/공간복잡도
  [원본 동작] -> [비용이 생기는 이유]
  -> 시간 : O(...) / 공간 : O(...)
  [개선 동작] -> [개선 효과]
  -> 시간 : O(...) / 공간 : O(...)

- 알고리즘 효율성 평가
  [입력 제한에서 현재 풀이의 시간·공간 비용이 적절한지와 근거]
  [불필요한 연산·메모리 사용과 개선 여지, 충분히 효율적이면 그 이유]

- 다른 알고리즘 / 풀이 방법
  [적용 가능한 대안의 핵심 아이디어와 적용 조건]
  [현재 풀이와 시간·공간복잡도, 구현 난이도, 장단점 비교]
  [현재 풀이 유지 또는 대안 선택의 이유]

- 오류 발생 가능성 / 핵심 수정
  [실제 문제와 발생 조건]
  [수정 방법과 이유]

- 코드 구조/간결성
  [핵심 개선 사항을 한 줄씩 작성]
*/
```

- 참조처럼 짧은 문장과 `->`로 원인·결과를 연결한다. 불필요한 장문 설명이나 모든 항목의 개선 코드 반복을 피한다. 기타 사항은 학습 가치가 있을 때만 `- 기타`로 추가한다.
- 참조 파일에 없더라도 알고리즘 효율성 평가와 다른 알고리즘 / 풀이 방법 항목은 포함한다. 유의미한 대안을 찾지 못하면 검토한 범위에서 현재 방식이 적절한 이유를 짧게 적고, 형식적인 대안을 만들지 않는다.
- 개선 전후 차이가 없으면 복잡도를 한 번만 적는다. 오류가 없으면 확인한 조건하에서 뚜렷한 오류를 찾지 못했다고 짧게 적는다. 의미 없는 지적을 만들지 않는다.
- 개선 코드는 주석 안 예시가 아니라 실제 풀이에 반영하고 원본 풀이를 하단 주석으로 남긴다. 제출용 함수·클래스 시그니처는 유지한다. 블록 주석 안에 기존 블록 주석이 있으면 줄 주석 등으로 보관하여 중첩 오류를 막는다.

## 분석 기준

- 코드와 확인한 문제 조건에 근거해 정확성을 설명한다. 필요한 제약이 없으면 가정을 명시하거나 공식 문제 설명을 확인한다. 확인하지 않은 정답 여부·제약을 단정하지 않는다.
- N, M 등 변수의 의미를 정의한다. 원본의 실제 동작으로 복잡도를 계산하고 중복 방문, 값 전달 복사, 정렬, 부분 배열 생성, 재귀 깊이 등을 반영한다. 표준 알고리즘 이름만 보고 복잡도를 대입하지 않는다.
- 입력 공간, 보조 공간, 컨테이너 복사 공간을 구분한다. 개선 후 복잡도가 달라지면 전후를 설명한다.
- 알고리즘 효율성은 복잡도 표기에 그치지 않고 확인한 최대 입력 크기와 시간·메모리 제한에 비추어 평가한다. 주요 병목과 불필요한 작업을 짚고, 점근적 개선과 상수 비용·가독성 개선을 구분한다. 제한이나 실행 근거가 부족하면 통과 여부나 최적성을 단정하지 않는다.
- 적용 가능한 다른 알고리즘이나 풀이 방법도 검토한다. 유의미한 대안은 핵심 원리, 성립 조건, 시간·공간복잡도, 구현 난이도와 장단점을 현재 풀이와 비교한다. 대안이 항상 더 좋다고 가정하지 않으며, 현재 풀이가 충분히 효율적이면 유지 이유를 설명한다. 대안 소개만을 위해 전체 구현을 추가하지 않는다.
- 문제점 → 영향이나 이유 → 구체적인 수정으로 가르친다. 정답 오류·성능 문제·스타일 제안을 구분하고, 실제 오류는 작은 반례나 실행 흐름으로 설명한다.
- 사용자의 알고리즘을 가능한 한 살린다. 다른 알고리즘이 실질적으로 유리하면 선택 이유와 복잡도 차이를 설명한다. 기본 정수형의 반환값을 쓰지 않는 i++/++i 같은 동등한 스타일을 성능 오류로 지적하지 않는다.
- BOJ의 stdin과 빠른 I/O, Programmers의 함수 인자·반환값, Leetcode의 클래스 메서드 형식을 구분한다. 프로그래머스의 main은 로컬 테스트용으로 보존하고 제출용 함수에 stdin 처리를 넣지 않는다.

## 알고리즘별 분류

- 리뷰와 함께 사이트·언어·핵심 알고리즘/자료구조를 판단하여 기존 `<site>/<lang>/<topic>/<subtopic>/` 트리로 이동한다. 파일명은 사이트별 규칙을 따르며 임의로 난이도를 추정하지 않는다.
- 분류는 결과 코드에서 문제 해결을 주도하는 기법을 기준으로 한다. 여러 기법을 쓰면 대표 폴더 하나에 저장하고 나머지는 문제 맵의 핵심 개념에 적는다. 예: 연결 요소를 BFS로 세는 네트워크 → `Programmers/Cpp/03_Graph/01_BFS_DFS/`.
- 이미 올바른 위치이면 유지한다. 미완성 풀이는 저장소의 `07_NotCompleted` 규칙을 따른다. 구현만 보고 해결 여부가 불확실하면 임의로 완료 처리하지 않는다.
- 목적지에 동명 파일이 있으면 내용을 비교하고 덮어쓰지 않는다. 판단할 정보가 부족한 경우에만 질문한다. 새 폴더는 기존 분류로 표현할 수 없을 때 만든다.
- 이동한 파일을 가리키는 저장소 내부 링크를 찾아 새 상대 경로로 갱신한다.

## README: 문제 맵과 주요 개념 요약

리뷰마다 루트 README와 목적지까지의 기존 상위 README 및 목적지 README를 확인해 필요한 내용을 갱신한다. 루트 README는 저장소 전체 탐색의 출발점, 상위 폴더는 하위 분류 맵, 말단 폴더는 개별 문제 맵과 해당 개념의 요약 역할을 맡는다. 말단 README가 없으면 만든다. 관계없는 폴더를 일괄 재작성하지 않는다.

- 루트: 실제 존재하는 사이트·언어·분류로 이동하는 상대 링크를 문제 맵에 제공한다. 모든 문제를 루트에 중복 나열하지 않고 상세 문제 맵으로 연결한다. 주요 개념은 분류별 핵심 아이디어와 상세 노트 링크로 짧게 요약한다. 소개·구조가 실제 저장소와 다르면 관련 부분을 수정한다.
- 상위 폴더: 실제 하위 분류 README에 연결하는 맵과 해당 범주의 주요 개념 요약을 둔다. 필요하면 직접 보관된 문제도 나열한다.
- 말단 폴더: `## 문제 맵` 아래에 `문제 | 풀이 | 핵심 개념` 표를 둔다. 문제 칸에는 파일에서 확인한 난이도·번호·문제명을 쓰고 풀이 칸은 소스의 상대 링크를 둔다. 공식 문제 URL은 확인된 경우에만 추가한다. 완료/미완성 등 상태가 필요하면 열을 추가하되 검증하지 않은 통과 상태를 만들지 않는다.
- `## 주요 개념 요약`에는 알고리즘의 적용 조건, 핵심 원리, 복잡도, 흔한 실수를 개념별 소제목과 짧은 항목으로 정리한다. 리뷰 전문·문제 설명·전체 코드를 복사하지 않는다. 문제를 새로 추가할 때 기존 개념을 확장하고 중복된 문제별 일지는 늘리지 않는다. 예제 출처는 관련 풀이로 연결한다.
- README의 사용자 작성 설명·기존 학습 노트·프로필 등은 보존한다. 기존 내용을 옮겨 정리할 때도 정보가 사라지지 않게 하며, 이미 적절한 구조면 필요한 항목만 추가한다. 해결 문제 수 등 집계를 넣는다면 실제 파일로 계산한다.
- 문제 표는 현재 폴더의 실제 풀이 파일과 대조해 누락·중복·오래된 경로를 정리한다. 링크는 README 위치 기준 상대 경로로 작성하고 존재 여부를 검증한다.
